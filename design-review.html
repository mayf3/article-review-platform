总诊断

当前产品最大的问题不是单个控件不好看，而是多角色工作流、API 契约、前端信息架构三者没有对齐。

当前 API 数据 47 篇 草稿 26、审稿中 15、已发布 6
前端可访问主页面 2 个 / 和 /articles/:id
详情页复杂度 884 行 数据获取、评论、审稿、diff、布局混在一个文件

目前它已经能作为本地文章看板和阅读器原型使用：中文 UI、状态列、Markdown 阅读、段落评论、审稿问题回复、版本 diff 都有雏形。 但从 README 的定位看，它要服务小博、人类用户、文风分析师、发布管家四类角色；实际前端只给了看板和文章详情，审稿队列、发布管理、 发布日志、设置、Agent 入口都只能通过 API 或文档访问。这会让“API 优先”变成“只有 API”，人类和 Agent 的协作上下文没有落到界面上。 

目标工作流:
小博写稿 -> 文风分析师审稿 -> 人类逐段确认 -> 发布管家多平台发布 -> 回写状态和日志

当前前端:
看板 -> 文章详情
     -> 评论/问题/diff 被塞进右侧栏
     -> 审稿队列、发布队列、日志、设置无页面入口

严重问题

这些会直接影响产品是否能支撑目标工作流。

critical 产品 / 信息架构

多角色工作流没有被前端路由承载，Agent 和发布管家的核心任务被隐藏在 API 里。

README 明确列出小博、人类用户、文风分析师、发布管家四类角色，并要求看板、阅读器、评论、审稿工作流、发布管理和 API 优先。 但 src/client/main.tsx:17-20 只注册了看板和文章详情。后端已有 /api/reviews/queue、 /publish-status、/publish-logs，前端没有对应队列页或管理页。

影响：15 篇 in_review 文章只能散落在看板列中，发布失败排查也只能 curl。协作型产品最关键的“下一步该谁做什么”没有变成第一屏信号。

建议：增加稳定 shell 和一级导航：看板、审稿队列、发布队列、文章详情、设置。审稿队列直接对接 /api/reviews/queue， 发布队列按 approved/publishing/failed 聚合平台状态和日志。

critical API 契约 / 文档可信度

公开文档、需求文档和真实路由存在多套契约，Agent 按文档集成会踩错接口或状态。

README 写的是 GET /api/articles/:id/content 和 /archive，平台指南写的是 /draft 和 /archives，前端调用的是 src/client/api.ts:113-117 的 /draft 和 /archives。 后端同时保留 src/server/routes/articles.ts:281-345 的旧 /content//archive 和 src/server/routes/files.ts:17-44 的新 /draft//archives，返回结构还不一致。

影响：这是 API-first 平台的信任问题。文风分析师或发布管家如果照 README 集成，得到的字段形状和前端预期不同，后续 diff、版本选择、任务状态会出错。

建议：确定一套 v1 API 契约，旧接口显式标为 deprecated，统一 OpenAPI/typed client/README/平台指南；把状态枚举、平台枚举、verdict 枚举放到共享 contract。

主要问题

这些不一定马上阻塞，但会持续拉低可用性、可维护性和扩展能力。

major 移动端 UX

移动端出现横向溢出，长标题和 Markdown 首行被截断。

Chrome headless 390×844 截图显示详情页标题只显示左半部分，正文 frontmatter 长行也横向溢出。代码上， src/client/pages/ArticleDetailPage.tsx:792-797 的标题没有强制断词，src/client/styles.css:30-105 的 Markdown 样式也没有 overflow-wrap 或 word-break 兜底。

建议：在详情页标题、slug、Markdown body、表格、代码和平台 chip 上补 min-width: 0、overflow-wrap: anywhere、 表格横向滚动策略；移动端将右侧面板改成真正的底部抽屉或标签视图。

major 数据模型

issue_tracking 表存在但没有成为问题追踪的事实来源。

数据库创建了 issue_tracking 表（src/server/db.ts:98-113），README 也宣称有“多轮问题追踪表”。 但 GET /api/reviews/issues/:articleId 在 src/server/routes/reviews.ts:181-245 里临时从 reviews JSON 聚合；作者响应只更新 reviews 的 issues JSON（src/server/routes/reviews.ts:252-303）。

影响：多轮问题追踪难以做稳定 ID、跨轮 merge、历史审计、按问题定位正文。后续一旦出现“同一问题描述变了”或“同一 location 多个问题”，追踪会漂移。

建议：要么删掉表并承认 MVP 使用 JSON，要么把 issue 创建、响应、状态变更全部落到 issue_tracking，reviews 只保留审稿快照。

major 前端架构

ArticleDetailPage.tsx 是一个 884 行巨型页面，交互状态和展示组件耦合过重。

这个文件同时负责 API 聚合、段落评论、回复、审稿问题响应、版本 diff、移动折叠面板、右侧栏、错误/loading 状态。 典型证据是状态集中在 src/client/pages/ArticleDetailPage.tsx:247-273，交互函数延伸到 :351-466，面板 JSX 延伸到 :553-730。

建议按业务切分：features/articles、features/comments、features/reviews、 features/versions。详情页只组合 layout；数据获取放到 hooks；评论线程、审稿问题、版本面板各自独立测试。

major 搜索 / 大数据量

看板搜索看起来是全局搜索，实际只过滤当前已加载页。

api.listArticles 支持 q（src/client/api.ts:89-97），后端也支持分页和搜索。 但看板的加载 effect 没有监听 filters.q（src/client/pages/KanbanPage.tsx:47-49），搜索逻辑在 :51-59 只过滤本地数组。当前 API 默认 pageSize 是 50，今天数据 47 篇还没暴露；一旦超过 50，搜索会漏结果。

建议：明确搜索范围。若是全局搜索，输入 debounce 后调用后端 q 并显示分页/结果数；若是当前页过滤，UI 文案应说“筛选当前列表”。

major 评论体验 / 可访问性

段落级评论只覆盖 p 标签，桌面添加入口依赖 hover，键盘用户难以发现。

MarkdownViewer 只重写 p 渲染（src/client/components/MarkdownViewer.tsx:28-68），标题、列表项、表格、 引用、代码块都不能直接评论。桌面“+”按钮在 :47 使用 opacity-0 group-hover，没有清晰的 focus 可见状态。 P1 文档要求“任意段落/标题旁边显示 + 按钮”和评论状态流转。

建议：用 Markdown AST 为 block node 生成稳定 block id；评论锚点基于 block id + line range，而不是仅 paragraph index。 添加常显或 focus-visible 的评论入口，并提供评论状态变更控件。

major 平台模型

平台枚举和真实数据不一致，发布管理会出现“能展示但不能创建/更新”的断层。

API 数据里出现了 zhihu、juejin、csdn、segmentfault 等 18 个平台值。 但服务端 PLATFORMS 只允许 github/wechat/feishu（src/server/types.ts:98-105）， 新建/更新时 normalizePlatforms 会过滤未知平台（src/server/routes/articles.ts:19-30）。

建议：把平台定义做成配置表或 settings API，至少区分“发布平台”和“内容分发标签”；前端不要从当前页数据临时推导所有平台选项。

major 性能 / 构建

首屏看板会打包详情页、Markdown 和 highlight.js，生产构建已出现大 chunk 警告。

src/client/main.tsx:4-5 同步导入 Kanban 和 ArticleDetail，MarkdownViewer 又在 src/client/components/MarkdownViewer.tsx:1 导入整个 highlight.js。本次 npm run build 产出 JS 约 1,354.83 kB，Vite 提示 chunk 超过 500 kB。

建议：对 ArticleDetailPage 做 route-level lazy import；按语言注册 highlight.js，或延迟到详情页代码块可见时再加载。

细节问题

这些属于体验和工程质量的局部摩擦，修起来成本低。

问题 证据 建议
开发脚本对端口占用不友好。 npm run dev 时 3000 被占用，server 直接抛 EADDRINUSE，client 自动切到 5174。脚本见 scripts/dev.mjs:3-13。 启动前探测 API 端口；支持 PORT=0 或明确复用已有 API；失败时给出可执行提示。
删除文章使用 window.confirm，缺少上下文和可恢复机制。 src/client/pages/KanbanPage.tsx:112-119。 用项目内 modal，明确“只删元数据、不删 draft.md”，并提供撤销或删除后 toast。
图标按钮和筛选控件的可访问性不稳定。 卡片删除按钮只有 title（src/client/components/ArticleCard.tsx:44-50），多个 select 依赖相邻文案或 title。 补 aria-label、显式 label、focus-visible 样式。
状态流转没有业务约束。 卡片里的状态下拉允许任意状态切换（src/client/components/ArticleCard.tsx:87-98）。 至少对发布中/已发布做确认，或显示合法下一步动作按钮。
类型和后端参数里仍有逃逸口。 @ts-ignore 出现在 src/server/routes/comments.ts:24-39；any 出现在 src/server/routes/reviews.ts:210、:267。 给 Express params 和 request body 加局部类型或 schema 校验。

修复优先级

按最小投入、最大收益排序。

先统一 API 和状态契约。

冻结 /draft//archives 或旧接口的去留，同步 README、平台指南、前端 api client、测试。否则后续页面越做越偏。

补全 AppShell 和一级导航。

新增审稿队列和发布队列入口，把 15 个待审任务、发布日志、失败状态变成可见工作流。

修移动端横向溢出。

这是可见质量问题，优先处理标题、Markdown、表格、代码块、平台 chip 和看板卡片。

把 ArticleDetailPage 拆成 feature 组件和 hooks。

先不大重构全项目，只拆详情页的评论、审稿、版本三个面板，收益最大。

决定问题追踪的事实来源。

若保留 issue_tracking，就让所有审稿和响应都写入它；若不保留，删表和文档承诺。

修搜索语义和分页。

把搜索变成后端全局搜索，或明确标注当前页过滤。

路由级代码分割。

懒加载详情页和 Markdown/highlight 依赖，消掉首屏大 chunk。

补可访问性和低成本交互 polish。

aria-label、focus-visible、删除确认 modal、状态流转确认、空态下一步动作。

实现风险

后续迭代最容易出问题的地方。

数据迁移风险

SQLite schema 直接在 initDb 里创建，缺 migration 版本。已有本地数据 47 篇，后续 schema 改动需要明确迁移策略。

协作契约风险

Agent 通过文档和 REST API 操作平台。只要 README、平台指南、前端 client、后端 route 不一致，失败会发生在人工难发现的位置。

长内容风险

真实文章含 frontmatter、长英文 tag、表格、代码块和多平台 chip。当前移动端已经溢出，后续评论锚点也会受 Markdown block 解析影响。

范围膨胀风险

发布管理、审稿触发、评论状态、历史恢复、设置页都在待办里。若继续把所有交互塞进详情页，会快速失控。
